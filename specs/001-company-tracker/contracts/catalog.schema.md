# Контракт каталога (GrokBot, сид, импорт, экспорт)

Агент наполняет список, не открывая UI: пишет файлы этой схемы. Значение ключа расшифровки в контракте **отсутствует** и MUST NOT появляться в примерах.

## Канонические пути

| Роль | Путь в репозитории | URL на сайте |
|------|--------------------|--------------|
| Данные | `public/data/companies.json` | `{VITE_BASE}data/companies.json` |
| JSON Schema | `public/data/companies.schema.json` | `{VITE_BASE}data/companies.schema.json` |

Это эквивалент `data/companies.json` / `data/companies.schema.json` из FR-013.

## Форма снимка

```json
{
  "schemaVersion": "1.0.0",
  "companies": [
    {
      "id": "acme",
      "name": "Acme",
      "website": "https://acme.example",
      "email": "jobs@acme.example",
      "coverLetter": "",
      "vacancies": [
        {
          "id": "fe-1",
          "title": "Frontend Engineer",
          "url": "https://acme.example/jobs/fe-1",
          "summary": "React TypeScript"
        }
      ]
    }
  ]
}
```

Полный снимок допустим: `email` открытым текстом, `coverLetter` — `""` или конверт `enc.v1`. Пример выше **намеренно** с пустым письмом: валидный публичный файл без демонстрации шифра и без секрета.

Невалидно в файле: открытый текст письма (любая непустая строка без префикса `enc.v1.`).

## Конверт `coverLetter`

```
enc.v1.<salt>.<iv>.<ct>
```

- `<salt>`, `<iv>`, `<ct>` — base64url без padding.
- Алгоритм, KDF, размеры, AAD — в [research.md](../research.md) и [data-model.md](../data-model.md).
- Агент, который хочет положить письмо в публичный файл, шифрует текст **у себя в памяти** ключом, который пользователь сообщил вне репозитория, и записывает только конверт. Ключ не коммитить, не печатать в схеме, не класть в `.env*`.
- Иначе агент оставляет `coverLetter: ""`; пользователь впишет письмо в UI.

Приложение читает ключ только так: `localStorage.getItem('sKey')`. Других каналов нет.

## Импорт и экспорт

Тот же `schemaVersion` и массив `companies`. Экспорт рабочей копии MUST шифровать непустые письма (или обнулять их с предупреждением, если `sKey` нет). Импорт невалидного файла отклоняется целиком.

Повторная запись с тем же `id` — обновление компании, не вторая карточка.

## Ошибки контракта

| Ситуация | Поведение |
|----------|-----------|
| Нет `schemaVersion` | Отказ |
| Мажорная версия ≠ 1 | Отказ |
| Компания без `id` или `name` | Отказ всего файла |
| Битый URL/email при непустом значении | Отказ всего файла |
| Вакансия без `id` / `title` / `url` | Отказ всего файла |
| `coverLetter` не `""` и не `enc.v1.…` | Отказ всего файла (это не «показать как письмо») |
| Нет `sKey` при чтении валидного конверта | Файл принять; письмо в UI не показывать |
| Есть `sKey`, конверт не расшифровался | Письмо этой компании не показывать; сырой конверт в UI не подставлять |

Проверка в коде (после implement): Zod в `src/lib/schema.ts`, конверт в `src/lib/letter-crypto.ts`.
