# Спецификация возможности: Трекер целевых компаний

**Ветка возможности**: `001-company-tracker`

**Создано**: 2026-10-05

**Статус**: Implement выполнен · ждёт converge

**Вход**: Пользовательское описание: «Удобное приложение для сохранения компаний, в которых пользователь хочет работать. Список компаний с полями имя, сайт, email; при наличии публичного API вакансий — список вакансий гиперссылками и фильтр по ключевым словам для фронтенда; textarea с сопроводительным письмом под компанию; хостинг GitHub Pages и хранение данных в браузере без серверной БД; явная схема и файлы/импорт, чтобы GrokBot мог наполнять список без UI.»

## Clarifications

### Session 2026-10-05

- Q: Откуда в первой версии должны браться вакансии компании? → A: Не из живого API. Основной путь — вручную добавить ссылку на вакансию в форме при создании или правке компании (вариант A: файл/импорт/форма, акцент на ручной ввод).
- Q: Кто задаёт ключевые слова фильтра вакансий «для фронтенда»? → A: Только встроенный фиксированный набор (хардкод). Пользователь набор не редактирует.
- Q: Какие поля GrokBot имеет право писать в публичный файл репозитория на GitHub Pages? → A: Вариант B — полный снимок, включая email и письма. Тексты писем в этом файле MUST быть зашифрованы. Ключ расшифровки читается только из `localStorage` по имени `sKey`. Значение ключа NEVER хранится в репозитории, спеке, README, примерах, тестах, сидах, `.env*` и комментариях: пользователь кладёт его в браузер руками (инструменты браузера или поле приложения, которое пишет только в `localStorage` имя `sKey`). Если `sKey` нет — письма не расшифровывать и не показывать открытый текст из файла.

## Пользовательские сценарии и тестирование

### Пользовательская история 1 — Вести список целевых компаний (Priority: P1)

Соискатель открывает приложение и видит свой список компаний, в которых хочет работать. Он добавляет компанию, задаёт имя, сайт и email, открывает карточку, правит поля и при необходимости удаляет компанию. Пустой список показывает понятное приглашение добавить первую компанию.

**Почему этот приоритет**: без списка компаний остальные возможности не имеют смысла. Это минимально ценный продукт.

**Независимое тестирование**: можно полностью проверить, создав, просмотрев, изменив и удалив компанию, даже если вакансии, письма и импорт ещё не сделаны.

**Сценарии приёмки**:

1. **Дано** пустое хранилище, **когда** пользователь открывает приложение, **тогда** он видит пустое состояние и может начать добавление компании.
2. **Дано** форма новой компании, **когда** пользователь указывает имя, сайт и email и сохраняет, **тогда** компания появляется в списке с этими тремя полями.
3. **Дано** существующая компания, **когда** пользователь меняет имя, сайт или email и сохраняет, **тогда** список и карточка показывают новые значения после перезагрузки страницы.
4. **Дано** существующая компания, **когда** пользователь подтверждает удаление, **тогда** компания исчезает из списка и больше не восстанавливается после перезагрузки (пока её снова не добавят или не импортируют).

---

### Пользовательская история 2 — Письмо именно под эту компанию (Priority: P2)

В карточке компании соискатель видит большое текстовое поле с сопроводительным письмом, подготовленным именно для этой компании. Он читает текст, правит его и при отклике копирует выделением в textarea (отдельной кнопки «Копировать» в v1 нет). У каждой компании своё письмо; чужое письмо не подставляется.

**Почему этот приоритет**: письмо — главная «заготовка» к отклику после самого списка. Без вакансий список и письмо уже полезны.

**Независимое тестирование**: открыть две компании, вписать разные письма, убедиться, что тексты не смешиваются и сохраняются после перезагрузки.

**Сценарии приёмки**:

1. **Дано** компания без письма, **когда** пользователь открывает карточку, **тогда** он видит пустое многострочное поле письма, привязанное только к этой компании.
2. **Дано** пользователь ввёл текст письма и ушёл со страницы, **когда** он снова открывает ту же компанию, **тогда** он видит тот же текст.
3. **Дано** две компании, **когда** пользователь меняет письмо компании А, **тогда** письмо компании Б не изменяется.

---

### Пользовательская история 3 — Вакансии компании и фильтр «для фронтенда» (Priority: P3)

Если у компании есть список вакансий, соискатель видит их как гиперссылки на страницу вакансии. Ссылки добавляют вручную в форме при создании или правке компании. На экране он включает фильтр по ключевым словам, относящимся к фронтенду, и видит только подходящие позиции. Если ссылок не добавляли, карточка остаётся рабочей: список, контакты и письмо не пропадают.

**Почему этот приоритет**: вакансии усиливают отклик, но компания полезна и без них. Живого API нет.

**Независимое тестирование**: в форме компании добавить ссылку на вакансию руками; карточка показывает гиперссылку. Компания без ссылок не ломается.

**Сценарии приёмки**:

1. **Дано** пользователь создаёт или правит компанию, **когда** он вручную указывает название и адрес страницы вакансии и сохраняет, **тогда** в карточке появляется гиперссылка на эту страницу.
2. **Дано** у компании есть вакансии с адресами страниц, **когда** пользователь открывает карточку, **тогда** он видит названия как ссылки, ведущие на страницу вакансии.
3. **Дано** список вакансий смешанный по специальностям, **когда** пользователь применяет фильтр по ключевым словам для фронтенда, **тогда** остаются только вакансии, чьи названия (и доступный текст) содержат хотя бы одно из этих слов; остальные скрыты, не удалены.
4. **Дано** фильтр не дал совпадений, **когда** список пуст после фильтра, **тогда** пользователь видит понятное пустое состояние и может выключить фильтр.
5. **Дано** у компании нет добавленных ссылок, **когда** пользователь открывает компанию, **тогда** он видит контактные поля и письмо, а блок вакансий — пустое состояние без ошибки всего экрана.

---

### Пользовательская история 4 — Данные живут в браузере, серверной БД нет (Priority: P2)

Соискатель пользуется приложением на статическом хостинге. Список, письма и вакансии, которые он уже видит, сохраняются локально на его устройстве. Закрытие вкладки не стирает данные. Отдельного сервера «базы компаний» нет.

**Почему этот приоритет**: без локального сохранения продукт на GitHub Pages непригоден после первой сессии.

**Независимое тестирование**: добавить компанию и письмо, полностью закрыть вкладку, открыть тот же адрес снова — данные на месте. Сетевых запросов к своей серверной БД нет.

**Сценарии приёмки**:

1. **Дано** пользователь сохранил компании в этом браузере, **когда** он закрывает вкладку и открывает то же приложение на том же устройстве и в том же браузере, **тогда** список и письма восстанавливаются.
2. **Дано** приложение открыто как статический сайт, **когда** пользователь сохраняет изменения, **тогда** запись выполняется в IndexedDB этого браузера, а не в серверную базу приложения. Это не облачная синхронизация.
3. **Дано** хранилище браузера очищено пользователем, **когда** он снова открывает приложение, **тогда** он видит пустой список (либо только публичный стартовый набор из репозитория — см. допущения) и понимает, что локальные правки потеряны.

---

### Пользовательская история 5 — GrokBot наполняет список без UI (Priority: P1)

Агент (GrokBot) добавляет или обновляет компании, не кликая по интерфейсу: он пишет файлы по явной схеме либо готовит файл импорта той же схемы. Пользователь открывает приложение и видит результат: либо после поставки обновлённых файлов сайта, либо после одного действия импорта. Агенту не нужен доступ к UI.

**Почему этот приоритет**: без машиночитаемого контракта агент не сможет надёжно наполнять список; это отдельное требование продукта, не «удобство разработки».

**Независимое тестирование**: подставить корректный файл данных / выполнить импорт, не пользуясь формой «добавить компанию», и получить те же поля в списке.

**Сценарии приёмки**:

1. **Дано** файл данных соответствует опубликованной схеме, **когда** агент записывает компании в канонический файл репозитория или пользователь импортирует этот файл, **тогда** приложение показывает эти компании с именем, сайтом, email, письмом и вакансиями.
2. **Дано** файл нарушает схему (нет версии, битые типы, неизвестная обязательная структура), **когда** выполняется загрузка или импорт, **тогда** приложение отвергает набор, не портит уже сохранённые валидные данные и объясняет, что файл не принят.
3. **Дано** компания с тем же стабильным идентификатором уже есть, **когда** агент передаёт обновлённую запись, **тогда** поля этой компании обновляются, а не создаётся неразличимый дубль с тем же id.

---

### Краевые случаи

- Пустой список: показывается пустое состояние, приложение не падает.
- Имя компании пустое: сохранение новой записи запрещено до появления имени.
- Сайт или email указаны, но в неверном формате: сохранение отклоняется с понятной ошибкой у поля; уже сохранённые другие компании не меняются.
- Две компании с очень похожими именами, но разными id: обе допустимы.
- Две записи с одним id: это обновление одной компании, не две карточки.
- Сопроводительное письмо очень длинное: поле принимает большой текст; если клиентское хранилище не вмещает набор, пользователь видит ошибку нехватки места и данные не «обрезаются молча».
- Вакансия без адреса страницы: не показывается как рабочая гиперссылка.
- Ссылку на вакансию не добавили: карточка жива, блок вакансий пустой, без ошибки экрана.
- Фильтр по ключевым словам не находит совпадений: пустое состояние фильтра, данные вакансий на месте.
- Импорт частично валиден: весь файл отклоняется (атомарно), чтобы агент и пользователь не получили «половину» набора. [если выбран другой режим — это должно быть явно подтверждено]
- Очистка данных сайта в браузере: локальная рабочая копия исчезает.
- Повторное открытие с другого устройства или другого браузера: локальные данные там не видны (нет серверной синхронизации).
- Канонические файлы в репозитории публичны на GitHub Pages. Полный снимок (включая email и письма) допустим; тексты писем в файле зашифрованы.
- В `localStorage` нет `sKey`: письма из файла не расшифровывают и открытый текст из файла не показывают.

## Требования

### Функциональные требования

- **FR-001**: Приложение MUST показывать список сохранённых компаний и карточку выбранной компании.
- **FR-002**: Пользователь MUST иметь возможность создать, изменить и удалить компанию через интерфейс.
- **FR-003**: У компании MUST быть поля: имя, сайт, email.
- **FR-004**: Имя компании MUST быть обязательным для сохранения. Сайт и email, если заполнены, MUST проверяться как адрес сайта и как email.
- **FR-005**: У компании MUST быть многострочное поле сопроводительного письма, относящееся только к этой компании. Приложение в первой версии MUST NOT само сочинять текст письма: оно хранит и показывает подготовленный текст (введённый человеком или пришедший из контракта агента).
- **FR-006**: У компании MAY быть список вакансий. Каждая показанная вакансия MUST быть гиперссылкой на страницу этой вакансии и иметь видимое название.
- **FR-007**: На экране вакансий пользователь MUST иметь возможность включить фильтр по встроенному фиксированному набору ключевых слов для фронтенда (хардкод в приложении). Пользователь MUST NOT редактировать этот набор. Фильтр MUST скрывать несовпавшие вакансии, не удаляя их из данных.
- **FR-008**: Вакансии MUST появляться как гиперссылки, которые пользователь добавляет вручную в форме создания или правки компании. Живого API списка вакансий нет. Файл сайта и импорт MAY тоже содержать ссылки, но основной путь — ручной ввод. Если ссылок нет, компания MUST оставаться пригодной для контактов и письма.
- **FR-009**: Рабочая копия каталога MUST храниться в IndexedDB. `localStorage` MUST использоваться только для имени ключа `sKey` (значение задаёт пользователь). Серверной базы данных приложения быть MUST NOT.
- **FR-010**: После закрытия и повторного открытия того же приложения в том же браузере пользователь MUST видеть ранее сохранённые компании, письма и локально сохранённые вакансии.
- **FR-011**: Продукт MUST поставляться как статический сайт, пригодный для GitHub Pages: без серверной среды выполнения и без серверных эндпоинтов приложения.
- **FR-012**: MUST существовать явная, версионированная схема набора данных (компании, письма, вакансии), достаточная, чтобы агент писал файлы без UI.
- **FR-013**: В репозитории MUST быть канонические файлы схемы и данных, которые агент может создавать и обновлять напрямую (`data/companies.schema.json` и `data/companies.json` либо эквивалентные пути, зафиксированные в контракте). Публичный файл MAY содержать полный снимок компании, включая email и письмо.
- **FR-014**: Пользователь MUST иметь возможность импортировать файл той же схемы в клиентское хранилище и экспортировать текущую рабочую копию в файл той же схемы (чтобы агент мог писать файл «снаружи», а человек — переносить снимок без UI-ручного ввода).
- **FR-015**: Импорт невалидного файла MUST быть отклонён целиком; уже сохранённая валидная рабочая копия MUST остаться нетронутой.
- **FR-016**: Компания MUST иметь стабильный идентификатор. Повторная запись с тем же идентификатором MUST обновлять компанию.
- **FR-017**: При нехватке места в клиентском хранилище приложение MUST сообщить об отказе сохранить и MUST NOT молча потерять часть полей.
- **FR-018**: Рабочая копия в браузере — источник правды во время сессии пользователя. Подхват данных из канонического файла репозитория при уже существующей локальной копии MUST происходить только как явное действие (импорт или сброс к файлу сайта), а не тихая перезапись писем пользователя.
- **FR-019**: Текст сопроводительного письма в каноническом публичном файле MUST быть зашифрован. Приложение MUST читать ключ расшифровки только из `localStorage` по имени `sKey`. Значение ключа MUST NOT попадать в репозиторий, документацию, примеры, тесты, сиды, `.env*` и комментарии. Пользователь кладёт значение в браузер руками: через инструменты браузера или через поле приложения, которое MUST писать только в `localStorage` имя `sKey` и MUST NOT копировать значение в IndexedDB, каталог, экспорт и логи. Если `sKey` отсутствует, приложение MUST NOT расшифровывать письма и MUST NOT показывать открытый текст письма, взятый из файла.

### Ключевые сущности

- **Компания**: организация, куда пользователь хочет устроиться. Обязательное имя; сайт; email; своё сопроводительное письмо; необязательный список вакансий; стабильный идентификатор.
- **Вакансия**: позиция у компании. Название и адрес страницы вакансии; при наличии — дата публикации и текст для фильтра.
- **Набор данных (каталог)**: версионированный снимок списка компаний в канонической схеме. Это то, что пишет GrokBot и что принимает импорт.
- **Рабочая копия**: экземпляр каталога в хранилище браузера конкретного пользователя на конкретном устройстве.

### Нефункциональные требования

- **NFR-001**: Приложение MUST работать как статически размещённый сайт (GitHub Pages): все страницы и данные поставки — файлы, без серверной БД и без своего backend API.
- **NFR-002**: Сохранение карточки MUST быть клиентской записью в IndexedDB: без серверного спиннера и без ожидания сети приложения. Отдельный численный бенчмарк задержки не требуется.
- **NFR-003**: Список из десятков компаний и писем MUST оставаться пригодным к просмотру и правке на обычном настольном браузере. Профилактическая мемоизация (`useMemo` / `useCallback`) и отдельный perf-бенч MUST NOT требоваться (конституция VI).
- **NFR-004**: Интерфейс MUST быть на русском языке (подписи, пустые состояния, ошибки импорта и хранилища).
- **NFR-005**: Основные действия (список, открытие карточки, поле письма, импорт) MUST быть доступны с клавиатуры и иметь доступные имена элементов.
- **NFR-006**: Файлы репозитория, попавшие на GitHub Pages, считаются публичными. Продукт MUST не создавать иллюзии «личной облачной базы»: интерфейс MUST коротко сообщать, что данные живут в этом браузере и между устройствами не синхронизируются.
- **NFR-007**: После первой загрузки сайта список, письма и уже сохранённые вакансии MUST быть пригодны без постоянного соединения. Живого запроса вакансий в v1 нет.

### Модель данных

Канонический снимок (файл и импорт) содержит:

- **schemaVersion** — строка версии схемы (несовместимая смена формата увеличивает совместимость-мажор).
- **companies** — массив компаний.

| Поле | Смысл | Обязательность |
|------|--------|----------------|
| `id` | Стабильный идентификатор для обновлений агентом | Обязательно |
| `name` | Отображаемое имя | Обязательно, непустая строка |
| `website` | Сайт компании | Если есть — корректный URL |
| `email` | Контактный email | Если есть — корректный email |
| `coverLetter` | Текст письма именно этой компании. В публичном файле — шифртекст; открытый текст только после расшифровки по `sKey` | Можно пустую строку |
| `vacancies` | Массив вакансий | Можно пустой массив |
| `vacanciesSource` | Необязательный указатель источника списка вакансий | Необязательно |
| `updatedAt` | Время последнего известного обновления записи | Необязательно |

Запись **вакансии**:

| Поле | Смысл | Обязательность |
|------|--------|----------------|
| `id` | Стабильный идентификатор вакансии внутри компании | Обязательно |
| `title` | Название для ссылки и фильтра | Обязательно |
| `url` | Адрес страницы вакансии | Обязательно для показа ссылкой |
| `publishedAt` | Дата публикации, если известна | Необязательно |
| `summary` | Короткий текст для фильтра, если известен | Необязательно |

Неизвестные поля при чтении более новой совместимой схемы MUST игнорироваться, а не ломать загрузку. Отсутствие `schemaVersion` или несовместимая мажорная версия MUST приводить к отказу импорта.

### Хранение в браузере

- Единственная база каталога в рантайме — IndexedDB (`idb-keyval`, ключ `job-searching:catalog`). `localStorage` — только имя `sKey`. MUST сохраняться тот же канонический снимок и MUST переживать перезагрузку вкладки. Это не облачная база.
- Серверной БД, аккаунтов и синхронизации между устройствами нет.
- Ключ/имя хранилища MUST быть зафиксированы и задокументированы, чтобы смена формата была явной (вместе с `schemaVersion`).
- Очистка данных сайта пользователем или другим профилем браузера удаляет рабочую копию.
- Лимит квоты браузера — ожидаемый отказ: сообщение, без тихой обрезки писем.
- Канонический файл в репозитории — стартовый/обменный снимок, не замена рабочей копии после того, как пользователь начал править данные локально (см. FR-018).

### Контракт заполнения GrokBot

Цель: агент наполняет список, не открывая UI.

1. **Схема** публикуется файлом `data/companies.schema.json` (или эквивалентом, названным в плане, но одним каноническим путём). Схема описывает набор и вложенные сущности из раздела «Модель данных».
2. **Данные** агент пишет в `data/companies.json` той же формы: `{ "schemaVersion": "1.0.0", "companies": [ ... ] }`.
3. Агент MUST выставлять стабильные `id` (чтобы повторный прогон обновлял компанию, а не плодил копии).
4. Агент MAY писать полный снимок: id, имя, сайт, email, вакансии и письмо. Поле письма в публичном файле MUST быть зашифровано. Ключ — только `localStorage.sKey`, значение задаёт пользователь вручную в браузере и его нет в репозитории.
5. **Импорт без поставки сайта**: пользователь загружает файл той же схемы в приложение; результат попадает в рабочую копию браузера. Это путь для файла, который агент создал локально и не закоммитил.
6. **Экспорт**: пользователь выгружает рабочую копию в файл той же схемы — агент может снова его прочитать и править.
7. Агенту достаточно схемы + примера валидного файла; клики по UI не требуются.
8. Невалидный файл агента не должен частично применяться (FR-015).

### Вакансии и фильтр по ключевым словам

- Вакансии — необязательное расширение карточки компании.
- Показ: название + гиперссылка на страницу вакансии (не «сырой» служебный адрес, если есть страница для человека).
- Фильтр выполняется на стороне клиента по уже имеющемуся списку вакансий этой компании. Слова ищутся без учёта регистра в `title` и в `summary`, если он есть.
- Фильтр не обращается к серверу приложения (его нет) и не удаляет вакансии из хранилища.
- Живого запроса к внешнему API нет. Основной источник вакансий — ручная ссылка в форме компании; файл и импорт могут содержать те же ссылки.
- Ключевые слова фильтра — только встроенный фиксированный набор для фронтенда; пользователь его не меняет.

### Ограничения GitHub Pages

- Только статические файлы: HTML/CSS/скрипты/данные. Нет серверного процесса, нет серверной БД, нет своего API-прокси.
- Клиентское хранилище привязано к происхождению сайта (адрес GitHub Pages). Другой адрес — другое хранилище.
- Любой файл в репозитории, который сайт отдаёт, публичен. Email в открытом виде и письма в виде шифртекста допустимы в каноническом файле. Открытый текст письма без `sKey` не показывают.
- Живого запроса к чужому API вакансий нет: ссылки задают вручную в форме (или приходят уже готовыми в файле/импорте).
- Нет серверной аутентификации: это личный трекер в этом браузере плюс необязательный публичный стартовый файл, не облачная база.

## Критерии успеха

### Измеримые результаты

- **SC-001**: Новый пользователь добавляет первую компанию с именем, сайтом и email и видит её в списке менее чем за 2 минуты, без инструкции «как устроен код».
- **SC-002**: В 100% проверок письмо компании А не появляется в карточке компании Б.
- **SC-003**: После закрытия вкладки и повторного открытия того же сайта в том же браузере 100% ранее сохранённых компаний и писем на месте (при нетронутом хранилище сайта).
- **SC-004**: Включение фильтра оставляет только вакансии, чьи `title` или `summary` содержат хотя бы одно встроенное слово; выключение тумблера возвращает полный сохранённый список без повторного ввода данных.
- **SC-005**: Агент, имея только схему и канонический файл (или файл импорта), добавляет не менее 3 компаний с письмами без единого действия в UI; пользователь видит их после обновления сайта или одного импорта.
- **SC-006**: Невалидный файл импорта в 100% таких попыток оставляет предыдущую рабочую копию без изменений.
- **SC-007**: Приложение пригодно к ежедневному использованию на GitHub Pages: пользователь выполняет просмотр списка, правку письма и копирование текста выделением в textarea без серверной БД и без регистрации.
- **SC-008**: Не менее 9 из 10 попыток открыть вакансию из карточки приводят на страницу этой вакансии (при корректно заданном адресе в данных).

## Допущения

- Один пользователь на браузер и устройство; учётных записей и общей облачной синхронизации нет.
- Язык интерфейса — русский.
- Это отдельное приложение для трекера компаний, не часть какого-либо нео-банка или другого продукта.
- В первой версии приложение не генерирует текст сопроводительного письма само: оно хранит подготовленный текст.
- Имя обязательно; пустые сайт и email допустимы; некорректный формат при непустом значении — ошибка.
- Стабильный `id` задаёт агент или приложение при создании в UI; уникальность в рабочей копии определяется `id`, а не именем.
- Конфликт «файл сайта уже обновили, а в браузере есть свои правки» разрешается в пользу рабочей копии, пока пользователь явно не импортирует файл и не сбросит данные.
- Импорт применяется атомарно ко всему файлу.
- Фильтр вакансий — клиентский, по текущему списку выбранной компании, не глобальный поиск по всем компаниям.
- Живого публичного API вакансий нет; ссылки добавляют руками в форме; карточка без вакансий валидна.
- Публичный файл MAY содержать полный снимок; письма в нём зашифрованы; ключ расшифровки — только `localStorage` имя `sKey`; значение пользователь кладёт руками (DevTools или поле, которое пишет только это имя).
- Целевой контекст — поиск работы во фронтенде; отсюда фильтр «для фронтенда», а не универсальная биржа труда.
- Поддерживаются современные настольные браузеры с клиентским хранилищем; отдельное нативное мобильное приложение вне объёма.

## Инфраструктура каркаса

Зафиксировано 2026-10-05. Полный трекер (CRUD, фильтр, импорт UI) ещё не реализован.

- **UI**: React + Vite + TypeScript (`strict`, без `any`).
- **Стили**: Tailwind CSS.
- **Проверки**: ESLint + typescript-eslint; Vitest + Testing Library.
- **Контракт GrokBot**: Zod-схема набора `companies`; канонические файлы `public/data/companies.json` и `public/data/companies.schema.json` (отдаются как `/data/…` — эквивалент пути `data/` из FR-013).
- **Хранилище**: IndexedDB, обёртка `idb-keyval`. Redux нет.
- **Хостинг**: GitHub Pages. Базовый путь задаётся `VITE_BASE` (`/` в разработке, `/job_searching/` в production). После сборки копируется `404.html` = `index.html` на случай будущих клиентских маршрутов.
- **Запрещено конституцией и здесь не используется**: преждевременные `useMemo` / `useCallback`, тип `any`, серверная БД.
