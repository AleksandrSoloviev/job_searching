# Исследование: Трекер целевых компаний

Все пункты Technical Context закрыты. Маркеров NEEDS CLARIFICATION нет: Q1–Q3 записаны в `spec.md` как официальные ответы пользователя (не допущения).

**Запрет на значение ключа**: ни одно решение ниже не содержит и не должно содержать секрет `localStorage.sKey`. Документируется только **имя** ключа.

## Q1. Источник вакансий

- **Decision**: живого API нет. Основной путь — ручной ввод названия и URL вакансии в форме создания или правки компании. Канонический файл и импорт MAY содержать те же поля `vacancies`.
- **Rationale**: официальный ответ clarify (вариант A). GitHub Pages не проксирует чужие API; карточка без ссылок остаётся рабочей.
- **Alternatives considered**: опрос внешнего API вакансий; гибрид файл+опрос. Отклонены ответом пользователя.

## Q2. Ключевые слова фильтра

- **Decision**: только встроенный фиксированный набор в коде (`BUILTIN_FRONTEND_KEYWORDS`). Пользователь набор не видит как редактор и не дополняет. Тумблер фильтра включает/выключает применение этого набора. Совпадение — подстрока без учёта регистра в `title` и `summary`. Фильтр скрывает, не удаляет.
- **Rationale**: официальный ответ clarify («А — хардкод»). Отдельное хранилище extra-keywords нарушает FR-007.
- **Alternatives considered**: только ручной ввод слов; встроенный набор ∪ пользовательские слова (неофициальное допущение v1). Отклонены.

Встроенный набор (константа кода, не секрет):  
`frontend`, `front-end`, `фронтенд`, `react`, `typescript`, `javascript`, `js`, `ts`, `html`, `css`, `next.js`, `nextjs`, `vue`, `angular`, `svelte`, `tailwind`.

## Q3. Публичный файл и письма

- **Decision**: публичный `public/data/companies.json` — полный снимок: `id`, `name`, `website`, `email`, `coverLetter`, `vacancies` (+ служебные). `email` в файле открытым текстом допустим. `coverLetter` в файле MUST быть пустой строкой или шифрконвертом `enc.v1`. Ключ расшифровки читается **только** через `localStorage.getItem('sKey')`. Если ключа нет или расшифровка не удалась — открытый текст из файла не показывают (поле письма в UI пустое, сырой конверт в textarea не подставляют). Рабочая копия в IndexedDB хранит уже открытый текст после успешной расшифровки или ввода пользователя.
- **Rationale**: официальный Q3 (вариант B + обязательное шифрование писем, FR-019).
- **Alternatives considered**: публичный файл без email/писем (неофициальное Q3=A); полный открытый текст писем в репо. Отклонены.

## Алгоритм шифрования письма

- **Decision**: Web Crypto, без npm-зависимости. На один непустой текст: случайные salt 16 байт и IV 12 байт; ключ = PBKDF2-HMAC-SHA-256 от значения `sKey`, 210_000 итераций, 256 бит; шифр = AES-256-GCM. AAD = UTF-8 `id` компании (конверт другой компании не расшифруется «как есть»). Строка в файле: `enc.v1.<salt>.<iv>.<ct>` (каждая часть — base64url без padding). Пустое письмо → `""`, без конверта. Экспорт/запись канонического файла: непустой открытый текст шифруется; если `sKey` нет — в файл уходит `""`, открытый текст MUST NOT писаться, пользователь видит предупреждение. Импорт/сид: конверт `enc.v1` + есть `sKey` → расшифровать; конверт + нет `sKey` → не расшифровывать, не показывать; строка не конверт и не пустая → считать письмом из файла недопустимой, не показывать как открытый текст.
- **Rationale**: стандарт браузера; соль на письмо и AAD закрывают подмену карточек; распознаваемый префикс отделяет конверт от случайного текста. Значение ключа в алгоритм не входит как константа.
- **Alternatives considered**: сторонняя crypto-библиотека (лишняя зависимость); сырой SHA-256 пароля без PBKDF2 (слабее при короткой фразе); отдельное поле-объект вместо строки (хуже для ручной правки JSON агентом).

## Где живёт ключ

- **Decision**: только `localStorage`, имя `sKey`. Приложение MAY дать поле ввода, которое вызывает `setItem('sKey', …)` / `removeItem('sKey')` и больше никуда значение не копирует (не IndexedDB, не каталог, не экспорт, не логи). Пользователь также MAY выставить ключ руками в инструментах браузера. Тесты создают временную фразу в памяти раннера (`localStorage` jsdom) и MUST NOT использовать пользовательский секрет.
- **Rationale**: FR-019 формулирует единственный канал чтения. Поле в UI не нарушает «руками в браузере» и не требует DevTools.
- **Alternatives considered**: ключ в `.env` / Vite define (попал бы в бандл или репо); ключ в IndexedDB рядом с каталогом (лишняя копия). Запрещены.

## Хранилище каталога

- **Decision**: IndexedDB через уже лежащую обёртку `idb-keyval`, ключ `job-searching:catalog`. Это единственная БД рабочей копии. Ключ `job-searching:extra-keywords` удалить при выравнивании с Q2.
- **Rationale**: письма длинные; квота больше, чем у localStorage как БД; имя уже зафиксировано каркасом.
- **Alternatives considered**: localStorage как основная БД каталога — отвергнут для длинных писем.

## Стек UI

- **Decision**: развивать существующий React + Vite + TS + Tailwind каркас.
- **Rationale**: уже собирается; конституция требует консистентности, не нового стека.
- **Alternatives considered**: новый фреймворк или Redux — лишняя сложность.

## Навигация

- **Decision**: один экран, без React Router. Список и карточка выбранной компании. Ручные вакансии — поля в той же форме.
- **Rationale**: десятки компаний; роутер не нужен. `404.html` остаётся на случай будущих маршрутов.
- **Alternatives considered**: отдельные маршруты `/` и `/companies/:id`.

## Сид, импорт, сброс

- **Decision**: пустой IDB → загрузить `{VITE_BASE}data/companies.json`, разобрать как файловый каталог (письма через правила конверта). Есть рабочая копия → сид не трогать (FR-018). Явный импорт заменяет рабочую копию целиком, если файл валиден. Явный сброс к файлу сайта — то же, что импорт текущего сида: публичные поля и email из файла; письма — только после успешной расшифровки. Невалидный файл — отказ, старая копия цела. Частичный импорт запрещён.
- **Rationale**: Q3=B значит сид может нести email и шифр писем; старое «беречь email при сбросе, потому что их нет в сиде» больше неверно.
- **Alternatives considered**: тихая перезапись при каждом деплое; сброс с мержем старых писем по id.
