# Конституция проекта Job Searching

## Основные принципы

### I. Единый кодстайл проекта

Весь код MUST следовать одному согласованному стилю форматирования,
импортов, именования файлов и структуры модулей, принятому в репозитории.
Личные предпочтения участника MUST NOT ломать существующий стиль.
Смешение нескольких стилей в одном изменении запрещено.

**Почему:** разнобой стилей замедляет чтение сильнее, чем любой локальный «улучшенный» вариант.

### II. Понятность новому разработчику за пять минут

Модуль, экран или контракт данных MUST быть понятны новому разработчику
примерно за пять минут без устных пояснений автора.
Имена, границы модулей и поток данных MUST делать намерение очевидным.
Если для понимания нужна «карта в голове автора» — устройство кода MUST быть упрощено.

**Почему:** приложение маленькое и должно оставаться читаемым без онбординга.

### III. Простота важнее сложности

Простое решение MUST быть выбрано вместо более сложного, если сложность
не устраняет конкретный, уже проявившийся недостаток.
Абстракции «на вырост», лишние слои и обобщения без второго потребителя запрещены.
Неочевидная сложность MUST быть явно обоснована в описании изменения.

**Почему:** лишняя архитектура дороже, чем прямое решение, в приложении без сервера.

### IV. DRY и явные имена

Повторяющееся правило, проверка или преобразование MUST жить в одном месте.
Имена MUST называть сущность и действие так, чтобы их нельзя было перепутать
с соседними (никаких `data`, `info`, `handleStuff`, `tmp2`).
Копирование блока «на всякий случай» запрещено: общее поведение выносится явно.

**Почему:** скрытое дублирование расходится; неявные имена порождают ошибки при правках.

### V. Минимум состояния и побочных эффектов

Состояние MUST храниться только там, где без него нельзя получить верный результат.
Побочные эффекты (запись в хранилище, сеть, навигация) MUST быть локализованы
и вызваны явным действием, а не «на всякий случай» при каждом рендере.
Один факт MUST иметь один источник правды; производные значения не дублируются в состоянии.

**Почему:** лишнее состояние — главный источник рассинхрона списка, писем и импорта.

## Ограничения качества кода

### VI. Без преждевременной оптимизации

Оптимизация MUST появляться только при измеренной или очевидной необходимости.
Мемоизация вроде `useMemo` / `useCallback` (если выбран такой стек) MUST NOT
добавляться «профилактически»: только при доказанном лишнем пересчёте
или стабильной ссылке, без которой поведение ломается.
Читаемость и простота MUST побеждать микрооптимизацию.

### VII. Строгая типизация без `any`

Тип `any` и скрытое ослабление типов запрещены.
Каждый публичный контракт (сущность компании, вакансия, файл импорта, хранилище)
MUST иметь явную полную схему типов.
Неизвестные внешние данные MUST проверяться на границе и сужаться до точного типа;
обход проверки запрещён.

### VIII. Без мёртвого кода и дублирующих комментариев

Неиспользуемые символы, ветки, стили и файлы MUST быть удалены в том же изменении,
которое сделало их мёртвыми.
Комментарий MUST объяснять неочевидное «почему», а не пересказывать «что» делает код.
Закомментированный код в поставке запрещён.

## Рабочий процесс

- Один запрос на слияние (PR) MUST решать одну задачу. Смешивать несвязанный
  рефакторинг, новую возможность и правку конституции в одном PR запрещено.
- Каждое изменение MUST оставить код не хуже, чем было: без нового дубля,
  без ослабления типов, без лишнего состояния и без падения читаемости.
- Консистентность с уже принятыми решениями репозитория важнее личных предпочтений.
  Отклонение MUST быть согласовано как поправка к конституции, а не как разовое исключение.

## Управление

Эта конституция имеет приоритет над локальными привычками и разовыми договорённостями в чате.
Поправки MUST быть записаны в этом файле с новой версией и датой.
Версионирование:

- MAJOR — удаление или несовместимый пересмотр принципа.
- MINOR — новый принцип или существенное расширение правила.
- PATCH — уточнение формулировок без смены смысла.

Перед слиянием ревьюер MUST проверить соответствие изменения принципам выше.
Необоснованная сложность, `any`, мёртвый код и «профилактическая» мемоизация — основание отклонить изменение.
Исключения MUST быть кратко обоснованы в описании PR и не становятся прецедентом без правки конституции.
